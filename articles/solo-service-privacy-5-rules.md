会社に勤めながら、個人で小さなWebサービスを公開しています。このとき最初に気をつけたのは、本名や会社のメールアドレスが、公開の場所に残らないようにすることでした。公開した情報は、後から消すのが大変だからです。

この記事は、私が自分のプロジェクトで実際に行っている5つの運用です。高度な技術は出てきません。どれも「公開する前」にやっておくと楽なものです。

## 実践1：最初の push の前に、コミットの作成者を noreply アドレスにした

Git のコミットには、作成者の名前とメールアドレスが記録されます。公開リポジトリに push すると、これは誰でも見られます。普段の git の設定に会社のメールが入っていると、そのまま履歴に残ります。

後から直すには履歴の書き換えと強制 push が必要で、手間もミスの危険も大きくなります。だから、最初の push より前にやるのが大事です。

### 手順

GitHub の Settings の Emails に、noreply アドレスが表示されます。形は `ID+ユーザー名@users.noreply.github.com` です（ここは画面に出る文字列をそのままコピーしてください）。同じ画面に「Keep my email addresses private」があり、オンにしておくのがおすすめです。

そのリポジトリだけに設定する例です。

```bash
git config user.name "表示したい名前（ハンドル名など）"
git config user.email "12345678+yourname@users.noreply.github.com"
```

`--global` を付けると、全リポジトリに効きます。会社の仕事でも同じ PC を使っているなら、全体の設定を変えると会社のリポジトリのコミットにも影響するので、リポジトリごとに設定するほうが安全です。

### 確かめ方

すでにコミットがあるなら、作成者を一覧で確かめます。

```bash
git log --format='%an %ae' | sort -u
```

出てきた名前とメールの組み合わせに、本名や会社のメールがないかを見ます。最初の push の前に、これを一度実行するだけで防げます。

GitHub には「Block command line pushes that expose my email」という設定もあります。オンにすると、非公開にしているメールが入ったコミットの push を止めてくれます。これも併せて使うと安心です（この2つの設定は、私もこれから見直す予定の「おすすめ」として挙げています）。

もし既に push してしまっていたら、履歴の書き換え（`git filter-repo` など）と強制 push が必要になります。他の人が clone していると影響が出るので、公開前の確認のほうがずっと楽です。

## 実践2：Google ログインで入った表示名を登録の最終画面で変え、アイコンも差し替えた

Zenn のようなサービスは、Google アカウントでログインして登録できます。便利ですが、Google アカウントの表示名とアイコンが初期値として入ります。ここに本名や顔写真が入っていると、そのまま公開プロフィールになります。

私は、登録の最終画面（プロフィールの入力）で、表示名と自己紹介を本名と関係のないものにしました。ただ、アイコンは Google の初期値のまま登録してしまい、登録の後に設定画面で別の画像に差し替えました。初期値のまま「登録」を押さず、アイコンまでその場で確かめるのが大事です。

あわせて、ユーザー名（URL に出る部分）も本名にしないほうが無難です。URL は記事のリンクとして外に広がるので、最初から本名と関係のない名前にしておくのが安全です。

## 実践3：問い合わせと登録は Google フォームで受け、電話番号は取らない

サービスへの問い合わせや事前登録は、自前のサーバーを持たず Google フォームで受けています。集める項目は、使い道のあるものに絞りました。

- 受けるのは、会社名・メールアドレス・従業員数・関心のあるサービス・有料での利用意向・気になっていることなど、提案や返信に使う項目
- 電話番号は取らない
- ページにも電話番号を載せない

項目を1つ足すたびに「これは何に使うか」を決め、使い道のないものは入れません。持っていない情報は、漏れようがありません。個人で運営していると、受け取った個人情報を守る負担も自分に来ます。集めないのが一番確実です。

そのうえで、プライバシーポリシーのページを置きました。何を集め、何に使い、どう扱うかを短く書いています。大げさな文書にはせず、実際にやっていることだけを書くのがコツです。書いた内容と実際の運用がずれないよう、項目を増やすときはポリシーも直します。

## 実践4：外形の点検は「外から誰でも見える情報」だけに限る

点検をするときは「外から誰でも見える情報だけ」を見る、と方針として決めています。たとえば DNS の SPF や DMARC の TXT レコードです。これは誰でも引ける公開情報です。

一方で、相手の許可なく、サーバーへポートを走査したり、脆弱性を探る通信を送ったりするような「能動的なスキャン」はしない方針にしました。

背景には、不正アクセス禁止法の考え方があります。許可なく他人のシステムにアクセスしてはいけない、というものです。私は法律の専門家ではないので、どこからが違法かの線引きは語れません。だから、判断に迷う領域には最初から入らない、という線の引き方にしました。自分が管理するもの、または相手から依頼を受けたものだけを対象にします。

SPF と DMARC の見方は、前の記事（https://zenn.dev/sec_madoguchi/articles/8b127af327e5e5 ）でも書いています。

## 実践5：パスワード・API キーの入力は人が行い、公開は別の確認を通す

文章の下書きやコードの作成には、AI のエージェントを使っています。ただ、次の2つには決まりを作りました。

- パスワードや API キーなど、秘密の情報の入力は、必ず人が行う
- 公開・送信・投稿といった取り消しにくい操作は、作った本人とは別の確認（チェック役の AI と私）を通してから行う

エージェントには、下書きの作成、ファイルの編集、確認用のコマンドの実行までを任せます。ログインが必要な画面や、鍵を入れる場面になったら、私が自分で入力します。外に出す操作（記事やページの公開）は、別の確認を通したうえで、記事の公開ボタンはこれまで私が押してきました。解説記事のように中身の確認が済んだものは、確認を通った後の公開手順を自動にすることも決まりの中で認めています。

理由は単純で、秘密の情報がエージェントとのやり取りの記録に残るのを避けたいことと、間違った内容がそのまま公開されるのを避けたいことです。作業の速さより、取り消せないものを公開前に確かめることを優先しました。

もう一つ、コードや設定ファイルに鍵を直接書かない（環境変数や別ファイルにして、リポジトリに入れない）ことも、方針として決めています。

## まとめ

| 実践 | 守るもの | やる時期 |
|---|---|---|
| コミットの作成者を noreply にする | 会社・個人のメール | 最初の push の前 |
| 表示名・アイコンを変える | 本名・顔写真 | 登録の最終画面（アイコンも） |
| 使い道のない項目・電話番号を取らない | 利用者の個人情報 | フォームを作るとき |
| 外から見える情報だけ点検する | 自分の立場 | 点検の前 |
| 秘密の入力は人・公開は別の確認の後 | 鍵・公開内容 | 常に |

どれも、公開してしまう前なら数分で済みます。個人でサービスを出す前の確認表として使ってもらえればと思います。
