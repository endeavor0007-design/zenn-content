生成AIに頼むと、ページやアプリは一晩でできあがります。ただ、AI は「動くこと」を優先して作るので、**公開してから困る所**は自分で見ておく必要があります。

この記事では、公開ボタンを押す前に見ておきたい8点を、**私が自分で運営しているサイト3つ（静的サイト・GitHub Pages）を実際に外から調べた結果**と一緒に書きます。うまくできていた所も、できていなかった所もそのまま載せます。

調べ方はどれも、ブラウザか `curl` で外から見える物だけです。他人のサイトに試すのはやめてください（自分の物か、許可をもらった物だけ）。

## 先に結論：8点と、私のサイトの結果

| # | 見る所 | 私のサイトの結果（2026-11-04 に調べ、11-08 に測り直し。4 だけは発行元の管理画面で入れた設定で、外からは測れません） |
|---|---|---|
| 1 | `http://` で開いたとき `https://` に移るか | ○ 3つとも 301 で移る |
| 2 | `.git` などの裏のファイルが開けないか | ○ 3つとも 404 |
| 3 | 公開するつもりのないファイルが出ていないか | △ 1つで README.md が開けた（中身は公開してよい説明文だった） |
| 4 | ブラウザに置いた鍵（API キー）に制限があるか | ○ 管理画面で制限を設定（外からは測れない）。ただし**ドメインを移したときに一度止まった** |
| 5 | 外から読み込むスクリプトが何本・どこからか | △ 3つとも計測用の1本だけ。改ざんの検知（SRI）は付けていない |
| 6 | フォームの入力がどこへ送られ、それをページに書いているか | ○ 送り先は Google フォーム。1つのページに運営者の欄が無かった→足した |
| 7 | セキュリティ用のヘッダー | × 付いていない（理由は後述） |

最初に調べたときは○が4つ、△が3つ、×が1つでした。6. はこの記事を書く中で直したので、いまは○が5つ、△が2つ、×が1つです。以下、1つずつ「何が困るのか」「どう確かめるか」「私のサイトでどうだったか」を書きます。

## 1. http で開いたとき https に移るか

**困ること**：`http://` のまま開けると、通信の途中で中身を見られたり書き換えられたりする余地が残ります。

**確かめ方**：

```bash
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" http://（自分のドメイン）/
```

`301` と `https://…` が出れば移っています。

**私のサイト**：3つとも `301` で https へ。GitHub Pages は設定の「Enforce HTTPS」に印を付けるだけで済みました。独自ドメインに替えた直後は証明書が出るまで印を付けられない時間があるので、替えた日に一度確かめると安心です。

## 2. .git などの裏のファイルが開けないか

**困ること**：サーバーに `.git` のフォルダごと置いてしまうと、過去の変更の履歴（消したはずのパスワードを含むこともある）を外から取り出される場合があります。AI に「このフォルダをサーバーに上げて」と頼んだときに起きやすい形です。

**確かめ方**：`https://（自分のサイト）/.git/HEAD` と `/.git/config` をブラウザで開く。

**私のサイト**：3つとも 404（開けない）。GitHub Pages はリポジトリの中身を出す仕組みで、`.git` 自体は出ません。自分のサーバーやレンタルサーバーに上げている場合は特に確かめてください。

## 3. 公開するつもりのないファイルが出ていないか

**困ること**：GitHub Pages のように「リポジトリの中身がそのままサイトになる」仕組みでは、**置いたファイルはすべて公開**です。作業のメモ、下書き、試しに書いた設定ファイルも、URL を知られれば読まれます。

**確かめ方**：公開しているフォルダのファイルの一覧を見て、「これは人に見られてよいか」を1つずつ答える。`README.md` や `memo.txt` など、よくある名前を直接開いてみるのも手です。

**私のサイト**：1つのサイトで `README.md` が開けました。中身はサービスの説明文で、公開してよい物でした。ただ、ここに作業のメモを書いていたら出ていたわけで、**「サイトのフォルダには、公開してよい物しか置かない」**と決めておくのが一番確かです。

## 4. ブラウザに置いた鍵（API キー）に制限があるか

**困ること**：ページの JavaScript に書いた鍵は、ブラウザの「ソースを表示」で**誰でも見られます**。AI は動かすために鍵をそのまま書き込むことがあります。

- 外に出してはいけない鍵（決済の秘密鍵、AI の API キーなど）は、**ブラウザ側に置かない**。サーバー側に置く
- ブラウザに置く前提の鍵（地図・商品検索などの「公開用」の鍵）は、**使えるサイトを自分のドメインに限る設定**を入れておく。ただしこの制限は、送り元のサイトの名乗り（Referer）を見るだけなので、偽って名乗られれば通ります。**他人に使われすぎるのを減らす物で、秘密を守る物ではありません**。見られて困る鍵は、この制限があってもブラウザに置かない

**確かめ方**：自分のページで「ソースを表示」し、`key`・`token`・`secret` で検索する。出てきた鍵の発行元の管理画面で、使えるサイトの制限が入っているかを見る。

**私のサイト**：相場を調べるページは、外部の商品検索のサービスをブラウザから呼ぶ作りです。発行元の管理画面で、使えるサイトを自分のドメインに限る設定を入れました（○。ただしこれは外から確かめられる物ではなく、自分の設定の記録です。上のとおり、使われすぎを減らすための制限です）。

ただ、ここで一度つまずきました。**サイトのドメインを github.io から独自ドメインに移したとき、鍵の「使えるサイト」に新しいドメインを足すまで、値段の自動表示が止まりました**。ドメインを替える・サブドメインを足すときは、外部のサービスに登録した「許可するサイト」も全部見直す、を手順に入れています。

## 5. 外から読み込むスクリプトが何本・どこからか

**困ること**：`<script src="https://よそのサイト/…">` で読み込んだ物は、相手のサイトが書き換えられると自分のページでも動いてしまいます。AI は便利な部品を気軽に足すので、知らないうちに本数が増えがちです。

**確かめ方**：ページのソースで `<script` を検索し、`src=` が自分のドメイン以外の物を数える。要らない物は外す。残す物は、可能なら `integrity="…"`（SRI：中身が変わったら読み込まない印）を付ける。

**私のサイト**：外から読み込んでいるのは、訪問を数える計測用の1本だけで、3つのサイトとも同じでした（2つは `<script src="//gc.zgo.at/…">` と `https:` を省いた書き方、残りの1つはページの中の短いコードから読み込む形でした。`src="https` で探すと3つとも見落とします。`<script` で探して、1本ずつ読み込み先を見るのが確かです）。この1本には SRI を付けていません。中身が更新されていく URL のままでは、SRI の値が合わなくなるので付けにくい形だと理解しています。配り元が版を固定した URL を用意していれば、それに替えて SRI を付けられます（その代わり、更新は自分で版を上げるまで止まります）。私は今は標準の URL のまま、「本数を増やさない・配り元を確かめてから使う」で抑えています。

## 6. フォームの入力がどこへ送られ、それをページに書いているか

**困ること**：お問い合わせや申し込みのフォームは、入力された名前やメールアドレスが**どこに保存されるか**が大事です。AI が作ったフォームは、送り先が仮のまま・どこにも届かない・誰でも見られる表に書かれる、ということがあります。また、集める側として「誰が運営していて、集めた情報をどう使うか」をページに書いておくと、申し込む人が安心できます。

**確かめ方**：自分で1回テストの送信をし、届いた先（表・メール）を誰が見られるかを確かめる。ページに運営者と、集めた情報の使い道が書いてあるかを見る。

**私のサイト**：申し込みの入口は、ページの中のフォームが1つと、Google フォームへのリンクが1つで、どちらも送り先は Google フォームでした（もう1つのサイトはメールで受け付ける形）。ただ、1つのページには**運営者の欄がありませんでした**（他の2つにはあった）。この記事を書くために見直して気づき、「運営事務局（個人運営）」という運営者の表記と問い合わせ先の行を足しました（2026-11-08 に公開中のページで確認）。

## 7. セキュリティ用のヘッダー

**困ること**：`Content-Security-Policy`（読み込んでよい物を決める）・`X-Frame-Options`（他のサイトに枠ではめ込まれるのを防ぐ）などのヘッダーは、うっかりの穴を小さくする安全網です。

**確かめ方**：

```bash
curl -sI https://（自分のサイト）/ | grep -iE "content-security|x-frame|x-content-type|strict-transport|referrer-policy"
```

**私のサイト**：何も出ませんでした（×）。GitHub Pages は自分でヘッダーを足す設定が無いためです。手は2つあります。

- `<meta http-equiv="Content-Security-Policy" content="…">` をページに書く（読み込んでよい物の制限はこれで効く。ただし、枠ではめ込まれるのを防ぐ指定〔frame-ancestors・X-Frame-Options〕は meta では効かない）
- ヘッダーを足せる配信の仕組み（CDN など）を前に置く

私のサイトは、ログインも決済も無い説明のページなので、今は付けずにいます。**ログイン・決済・個人の情報の表示があるアプリなら、付けてから公開**をおすすめします。

## 8. 独自ドメインでメールを使うなら SPF・DMARC

**困ること**：設定が無いと、自分のドメインを名乗った迷惑メールを止めにくく、自分が送ったメールも迷惑メールの箱に入りやすくなります。

**確かめ方**（Windows なら `nslookup`）：

```bash
nslookup -type=TXT （自分のドメイン）
nslookup -type=TXT _dmarc.（自分のドメイン）
```

`v=spf1 …` と `v=DMARC1 …` が出ればあります。

**私のサイト**：両方あります。DMARC は `p=none`（届いた結果を見るだけの様子見）にしていて、しばらく報告を見てから強める予定です。

## まとめ：公開前の10分でできること

1. `http://` で開いて https に移るか
2. `/.git/HEAD` が開けないか
3. サイトのフォルダに、見られて困るファイルが無いか
4. 「ソースを表示」で鍵を探し、使えるサイトの制限を確かめる（ドメインを替えたら見直す）
5. よそから読み込むスクリプトを数える
6. フォームの送り先と、届いた物を誰が見られるか・運営者の欄を確かめる
7. ヘッダーを `curl -I` で見る
8. メールを使うなら SPF・DMARC

私も自分のサイトで △ が2つと × が1つ残っています。全部を○にするより、**「どこが × で、なぜ今はそれでよいか」を自分で説明できる**状態にしておくのが、小さく作って出すときの現実的な線だと考えています。
